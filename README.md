# AELITA PRODUCTION — сайт

**Версия: `aelita-v59`**

📄 Пошаговая инструкция по развёртыванию в PDF: `Documents/SetupGuides/AELITA-setup-site.pdf`

Статический сайт театральной продюсерской компании AELITA PRODUCTION.
Домен: **aelita-production.ru** (GitHub Pages, см. `CNAME`).

Чистый HTML/CSS/JS без сборки — что лежит в репозитории, то и деплоится.

## ⚠️ Правило при любой правке стилей

Перед тем как считать правку CSS законченной — обязательно:

1. **Проверить баланс скобок** во всех затронутых файлах (и в самом
   `assets/style.css`, если он менялся) — одна лишняя или недостающая `{`/`}`
   ломает всё, что идёт после неё в файле.
2. **Проверить, что вычисленный эффективный стиль не изменился там, где
   не должен был** — особенно если правишь `assets/style.css`: у страниц
   могут быть свои локальные правила с тем же селектором (см. раздел про
   каскад ниже), и невинная на вид правка в одном месте может тихо
   изменить вид на 5 других страницах.
3. **Задокументировать в этом README** — что изменилось и почему. Не
   «чтобы было», а потому что этот файл — единственное место, где
   зафиксировано, какие решения приняты осознанно (например, разный
   `--maxw` у юр.страниц) и какие классы имеют «двойное дно» (`.page-hero`,
   `.hero-sub`) — без этого следующая правка почти гарантированно
   наступит на те же грабли, что уже наступали здесь дважды.

Если правка мелкая и точечная — пункт 3 может быть одной строкой в
соответствующем разделе. Но пропускать его не надо.

## ⚠️ Правило при добавлении/удалении страницы

Если появилась новая страница (новая папка + `index.html`) или старая
удалена — сразу же:

1. Добавь/убери её в `sitemap.xml` (кроме `404.html`, `offline.html` —
   их там никогда не было и не должно быть, и кроме `oferta`/`privacy`/
   `cookies`/`bot`/`admin` — они закрыты в `robots.txt`, см. раздел ниже).
2. Проверь, что на неё есть хотя бы одна ссылка с сайта (из футера, нав-меню
   или связанной страницы) — иначе она физически существует, но её никто
   не найдёт кроме как по прямому адресу. Исключение — `admin` (см. `##
   Админка` ниже): туда сознательно нет ссылок ни с одной страницы сайта,
   доступ только по прямому адресу.
3. Если это самодостаточная страница (не подключает `assets/style.css`) —
   впиши её в список исключений в разделе «CSS: как устроено» выше.

Быстрая проверка после правки — сверить список папок сайта со списком
`<loc>` в `sitemap.xml`: должны совпадать один в один (минус
самодостаточные `404`/`offline` и страницы, закрытые в `robots.txt` —
`oferta`/`privacy`/`cookies`/`bot`/`admin`).

## ⚠️ Версия

Каждое обновление сайта — новый номер версии в формате `aelita-vN`
(строка в самом верху этого файла). При любой правке, после которой
собирается новый архив на выдачу:

1. Увеличить номер на 1.
2. Сообщить номер отдельно, явно — не прятать в середине ответа.

Так проще сослаться на конкретную версию в переписке, если что-то нужно
будет откатить или сверить.

## Развёртывание с нуля (GitHub Pages)

Домен закреплён в `CNAME` (файл в корне `Site/`, содержит одну строку
`aelita-production.ru`) — GitHub Pages читает его сам, руками ничего
прописывать в коде не нужно, но сам GitHub и DNS настраиваются один
раз вручную:

1. **Репозиторий.** Создать репозиторий на GitHub, залить в него
   содержимое папки `Site/` **в корень репозитория** (не в подпапку —
   иначе адреса вида `/tickets` не будут работать без `/Site/` в
   начале).
2. **Включить Pages.** Repository → Settings → Pages → Source:
   `Deploy from a branch` → выбрать ветку (обычно `main`) и папку
   `/ (root)` → Save. Через минуту-две GitHub выдаст временный адрес
   вида `<username>.github.io/<repo>` — на этом шаге сайт уже
   работает, просто не на своём домене.
3. **Свой домен.** В том же Settings → Pages → Custom domain — вписать
   `aelita-production.ru` (файл `CNAME` в репозитории появится/
   обновится сам). Затем у регистратора домена (там, где куплен
   `aelita-production.ru`) добавить DNS-записи, которые требует
   GitHub — на момент написания это A-записи на IP GitHub Pages
   (`185.199.108.153`, `.109.153`, `.110.153`, `.111.153`) для голого
   домена и CNAME на `<username>.github.io` для `www` — актуальный
   список IP смотреть в официальной документации GitHub Pages
   («Managing a custom domain»), он иногда меняется.
4. **HTTPS.** GitHub сам выпускает сертификат через Let's Encrypt
   после того, как DNS начнёт указывать правильно (может занять от
   нескольких минут до суток) — в том же разделе Settings → Pages
   появится галка «Enforce HTTPS», включить её, как только она
   станет доступна (недоступна, пока сертификат не выпущен).
5. **Проверка.** Открыть `https://aelita-production.ru` — если
   не работает сразу, смотреть Settings → Pages: там GitHub прямо
   пишет текущий статус («DNS check successful» / ошибку) — не гадать
   по симптомам, эта страница обычно точно говорит, что не так.

Сборки нет — что лежит в репозитории, то и отдаётся как есть, никаких
`npm run build`/CI-шагов. Обновление сайта — это просто новый commit
в ветку, которую видит Pages (задержка публикации — обычно меньше
минуты).

## Внешние зависимости (JS, pack-v201)

Весь сайт до сих пор был на собственном коде — ни одной подключённой
внешней JS-библиотеки нигде (только изображения со старого Tilda-CDN,
оставшиеся с миграции, не скрипты). Первое исключение —
`Site/tickets-scan/index.html`: камера-сканер QR подключает **jsQR**
с cdnjs (`cdnjs.cloudflare.com/ajax/libs/jsqr/1.4.0/jsQR.js`).
Причина — писать свой декодер QR из кадров видео несоразмерно задаче,
а самостоятельно захостить файл в момент правки было нечем (в
контейнере сборки пака нет сети, тот же ограничитель, что у
`_tools/DesignSystem/qr_gen.py`). Если понадобится убрать внешнюю
зависимость — файл jsQR один, ~30 КБ, скачать и положить в
`/assets/jsQR.js`, поменять `src` в `tickets-scan/index.html` на
локальный путь. Страница и так служебная (`SKIP_SLUGS`, доступ только
персоналу), к публичным страницам сайта это правило не относится, но
и там намеренно ничего внешнего не подключалось — держаться той же
практики, если понадобится JS где-то ещё.

## ⚠️ CSS: как устроено и что нельзя ломать

Стили лежат в двух местах:

1. **`assets/style.css`** — общее для всего сайта: шапка, мобильное меню, футер,
   кнопки, карточки событий, брейкпоинты. Подключается через
   `<link rel="stylesheet" href="/assets/style.css">`.
2. **`<style>` внутри каждой страницы** — то, что уникально именно для неё
   (свои отступы hero-блока, свой `--maxw`, специфичные компоненты).

**Четыре страницы НЕ подключают `assets/style.css` вообще** и должны быть
полностью самодостаточны — весь нужный CSS у них внутри `<style>`:

- `404.html`
- `offline.html`
- `app/index.html`
- `admin/index.html` — внутренняя админка (см. `## Админка` ниже),
  добавлена в `aelita-v32`; самодостаточна по другой причине, чем
  первые три (не про отказоустойчивость, а про изоляцию — страница не
  для публики, не должна тянуть за собой общий CSS/навигацию сайта)

Это осознанно: страница 404 и офлайн-заглушка обязаны отрисоваться, даже
если с сайтом или сетью что-то не так. Если добавляешь этим страницам
новый визуальный элемент — стили для него нужно писать **прямо в их
собственном `<style>`**, не полагаясь на общий файл.

### Главное правило при правке общих стилей

Внешний `assets/style.css` в каскаде всегда идёт **раньше** локального
`<style>` страницы. Значит:

- Если у страницы есть **своё** базовое правило для селектора (например,
  свой `.sec-head{margin-bottom:...}`), а в `assets/style.css` для этого же
  селектора добавить `@media(...)`-переопределение — оно **не сработает**
  на этой странице, потому что локальное правило (без медиа-условия) всегда
  идёт позже и просто перебивает медиа-запрос.
- Если правишь что-то в `assets/style.css`, **проверяй, нет ли у страниц
  своего локального правила с тем же селектором** — если есть, адаптивное
  переопределение нужно продублировать и в `<style>` этой страницы тоже.
- В `assets/style.css` не должно быть **двух голых (без `@media`) правил
  для одного и того же селектора** — выигрывает то, что физически ниже по
  файлу, и это легко случайно поломать одной группе страниц в пользу другой.

Если что-то в вёрстке выглядит иначе на разных страницах непонятно почему —
в 9 случаях из 10 причина именно в этом.

### `:root{--maxw}`

Ширина контейнера контента — переменная, разная для двух групп страниц:
- `1320px` — все обычные страницы (задано в `assets/style.css` по умолчанию)
- `900px` — юридические страницы (`oferta`, `privacy`, `cookies`,
  `documents`, `bot`), заданы локально в каждой из них

## Юридические страницы и индексация

`robots.txt` закрывает от индексации `/oferta`, `/privacy`, `/cookies`,
`/bot` — это осознанно, не баг. При добавлении новой страницы не забудь
внести её в `sitemap.xml`.

(До этой правки `/bot` в этот список не входил — недосмотр, не
осознанное решение; исправлено. `robots.txt` не входит в
`PRECACHE_URLS` в `sw.js`, поэтому для этой правки бампать
`SITE_VERSION` не требовалось.)

## Админка (`/admin`, aelita-v32)

Внутренняя страница для команды — список клиентов личного кабинета,
их покупки, агрегированная выручка, ссылки на недельный отчёт
аналитики и личный кабинет ЮKassa. Полная документация (модель
авторизации, деплой, осознанные границы — что показывает сама, что
даёт только ссылкой, что не делает вообще) — `_tools/Admin/README.md`,
не дублирую здесь.

Коротко про сам сайт:
- `admin/index.html` — самодостаточная страница (см. «CSS: как
  устроено» выше), не подключает `assets/style.css`, весь CSS внутри.
- `robots.txt` закрывает `/admin` от индексации (тот же список, что
  юридические страницы выше).
- НЕ в `sitemap.xml`. В `SKIP_SLUGS` переводческого пайплайна
  (`_tools/DesignSystem/i18n/core.py`) — намеренно ДОБАВЛЕН, страница
  не переводится на английский вообще, это внутренний инструмент для
  русскоязычной команды, не часть двуязычного публичного сайта.
- НЕ подключает `assets/analytics-events.js` — в списке исключений
  `ANALYTICS_EXEMPT` в `_tools/Audit/run_audit.py`: трекать поведение
  сотрудников тем же публичным счётчиком, что и посетителей сайта,
  незачем.
- НЕТ ссылки на `/admin` ни с одной страницы сайта (ни в футере, ни в
  навигации) — единственное сознательное исключение из правила
  «Правило при добавлении/удалении страницы» выше (пункт 2): доступ
  только по прямому адресу, кому надо — тот знает адрес.

## Скачивание PDF-версий документов (aelita-v16)

У `/oferta`, `/privacy`, `/cookies`, `/bot` и на хабе `/documents` теперь
есть кнопка «Скачать PDF» — ссылка на `documents-pdf/{oferta,privacy,
cookies,bot}.pdf`. PDF генерируются скриптом
`Documents/Legal/_sources/build_site_docs.py`, который читает текст
**напрямую из HTML этих страниц** — юридического текста в скрипте нет,
единый источник — сайт (так с pack-v31; раньше текст был продублирован
в скрипте и один раз уже разошёлся с сайтом — см. CHANGELOG, pack-v26).

При правке текста документа:

1. поправить текст в `Site/<doc>/index.html` — это всё, что касается
   содержания;
2. перезапустить `python3 Documents/Legal/_sources/build_site_docs.py`
   (пути в нём относительные, работает из любого места);
3. скопировать 4 файла из `Documents/Legal/` в `Site/documents-pdf/`
   под латинскими web-именами (`oferta.pdf` и т.д.);
4. если менялись CSS/JS — бампнуть `SITE_VERSION` в `sw.js` и все
   `?v=N` (см. раздел про кэш ниже); для правки только текста и PDF
   это не требуется.

Скрипт опирается на разметку страниц: `<h1>`, `<p class="doc-meta">`,
`<div class="doc-body">`, `<h2>` вида «N. Название», `<div
class="req">`. Если менять структуру этих страниц — проверить, что
скрипт всё ещё собирает документы целиком (после сборки он печатает
число разделов; сверить с сайтом).

Клики по скачиванию уходят в Яндекс.Метрику как `legal_pdf_download`
(см. `assets/analytics-events.js`) — тем же паттерном, что и клики по
телефону/почте/Telegram.

## Аналитика

**Три независимые системы, дополняют друг друга:**
- **Яндекс.Метрика** — счётчик `104681911`. GA4 на сайте нет и никогда
  не было подключено (см. историю правок ниже, «Убрано упоминание
  Google Analytics») — не путать мёртвый код с живой интеграцией,
  если наткнётесь на упоминания gtag в старых заметках.
- **Пиксель VK Рекламы** — технически это счётчик top.mail.ru
  (`assets/main.js`, `loadVkPixel()`/`VK_PIXEL_ID`): после перехода
  на новый рекламный кабинет VK Рекламы (28 января 2026) старый
  JS API ретаргетинга (`VK.Retargeting.Init`) не работает, новый
  пиксель выдаётся именно в таком виде. **`VK_PIXEL_ID` пока `0`** —
  пиксель ещё не создан в кабинете `ads.vk.com` (раздел «Сайты» →
  «Добавить пиксель»); пока так, счётчик намеренно не грузится
  вообще, не подставлена нерабочая заглушка. Заполнить `VK_PIXEL_ID`
  в `main.js`, id тот же, что у пикселя в кабинете. Те же именованные
  цели, что уходят в Метрику (см. `analytics-events.js`, `track()`),
  дублируются и в пиксель (`window._tmr`, `reachGoal`), как только
  `VK_PIXEL_ID` заполнен — отдельно их описывать не нужно.
- **Собственная система** (`_tools/Analytics/`, с pack-v110) — сырые
  события (просмотры страниц + те же категории кликов) в собственной
  Google Таблице, без зависимости от внешнего сервиса. Подробности,
  деплой, приватность — `_tools/Analytics/README.md`.

**Два файла:**
- `assets/main.js` — сама установка счётчика (`loadMetrika()`), под
  cookie-согласием: до принятия баннера счётчик не грузится вообще,
  ни в каком виде — это не декоративная задержка, а фактическое
  отсутствие трекинга без согласия, так соответствие 152-ФЗ/GDPR
  честное, не формальное. `clickmap:true` и `trackLinks:true` в
  инициализации дают базовую тепловую карту кликов и трекинг внешних
  ссылок «из коробки», без единой строчки кастомного кода — то, что
  описано ниже, поверх этого, для именованных целей, которые видно в
  отчёте «Цели», а не только на тепловой карте.
- `assets/analytics-events.js` — именованные цели поверх встроенного
  трекинга: `phone_click`, `email_click`, `telegram_channel_click`/
  `telegram_bot_click`, `festival_tickets_click` (внешняя продажа на
  cuire-fest.ru — это и есть настоящая конверсия, не переход на
  внутреннюю `/tickets`), `tickets_page_click` (сама внутренняя
  страница), `legal_pdf_download` + `cv_download` (по регэкспу на имя
  файла `*-cv.pdf`, не по жёсткому списку имён — новый человек не
  требует правки сюда), `show_card_click` (карточки спектаклей —
  `work-card`/`show-card`/`proj-card`/`prog-item`, с какой именно
  карточки и на какой слаг), `person_card_click` (`speaker-card`/
  `partner-card`), `drive_doc_click`, `cuire_fest_outbound_click`
  (общий улов на любую ссылку на cuire-fest.ru, не попавшую в правило
  выше — подстраховка на новый тип ссылки), `pwa_install_click`,
  `form_submit_click`, `video_sound_on`. Подключён `<script>`-тегом на
  каждой странице отдельно (не через `main.js`) — при добавлении
  новой страницы не забыть этот тег; с pack-v101 это проверяется
  автоматически (`_tools/Audit/run_audit.py`, категория `analytics`) —
  ловит именно так, как поймал сам при первом прогоне: страницы
  `/app/` и `/en/app/` (полноценная страница установки PWA, с той же
  кнопкой `install-btn`, для которой только что добавлено отслеживание)
  были без тега вообще — тег добавлен, поймано до сдачи, не оставлено
  как есть.

**Покупки на самом сайте (community/консьерж/подарочная карта/
программка) — серверная конверсия «purchase» в Метрику**, не
клиентский `ecommerce:"dataLayer"` (тот по-прежнему включён в
инициализации счётчика, но ничего в него не пушится — честнее было
не подключать в дополнение вторую, дублирующую схему события). Цепочка
— `Site/assets/payments.js` (`getYmClientId()`, ClientID Метрики) →
`_tools/Payments/create-payment.js` (кладёт его в `metadata.
yandex_client_id`) → `_tools/Payments/webhook.js`
(`sendPurchaseGoalToMetrika`, отправляет реальный факт оплаты через
Measurement Protocol, `mc.yandex.ru/collect`) — не клик по кнопке
«Оплатить», а именно подтверждённый ЮKassa платёж. Требует токен
Measurement Protocol счётчика в переменной окружения
`YM_MEASUREMENT_TOKEN` (см. `_tools/Payments/README.md`) — без него
просто не отправляется, остальная оплата не страдает. ⚠️ Реализовано
по документированным полям Measurement Protocol — точный список
необязательных полей события Яндекс нигде подробно не документирует,
сверить на тестовом платеже перед запуском рекламы (см. комментарий в
`webhook.js`).

**Чего в статистике сознательно нет и почему:**
- **Ecommerce-событие для внешней продажи билетов** — продажа билетов
  на сами спектакли/фестиваль идёт на cuire-fest.ru, не на этом
  сайте — здесь физически нет момента оплаты, чтобы его затрекать.
  `festival_tickets_click` — максимум, что можно honestly померить с
  этой стороны: сайт видит переход на билеты, не видит, купили ли.
- **Итог по факту продаж со стороны cuire-fest.ru** — если у
  фестивала есть доступ к их аналитике (или готовы поделиться цифрой
  продаж, пришедших с aelita-production.ru), это единственный способ
  увидеть конверсию клика в реальную покупку. Ссылки на
  `cuire-fest.ru/tickets/` теперь идут с UTM-меткой
  (`utm_source=aelita-site&utm_medium=referral&utm_campaign=site&
  utm_content=<страница>`) — если фестиваль умеет это фильтровать,
  этого достаточно для сверки со своей стороны; сама AELITA эти
  переходы дальше cuire-fest.ru всё равно не видит.
- **Скролл-трекинг** — не реализован. Полезен на длинных страницах
  (`/tochkacuire`, отдельные страницы спектаклей), но не подключён —
  решение сознательно не принято ни за, ни против, просто отложено.

## Выдача в соцсетях (Open Graph / Twitter Card, aelita-v47)

Полный набор тегов (`og:type/url/title/description/image/locale/
site_name` + `twitter:card/title/description/image`) обязателен на
каждой публичной странице — проверяется вручную одноразовым скриптом
(не входит в постоянный `run_audit.py`, стоит завести отдельной
категорией, если правки в этой области продолжатся). Осознанные
исключения без OG: `/admin` (внутренняя, не индексируется),
`/tochkacuiri` (redirect-заглушка на `/tochkacuire`, см.
`ANALYTICS_EXEMPT` в `assets/analytics-events.js` — тот же список
причин), `404.html`/`offline.html`.

**`og:site_name`** — `AELITA PRODUCTION` на каждой странице, значение
не переводится (латиница уже сама по себе), i18n-пайплайн его
пропускает автоматически без записи в словарь.

**`og:image`/`twitter:image` — размер 1200×630** (`images/og-
default.jpg`, общий фолбэк). Если у страницы своя картинка — та же
пропорция ~1.91:1, никогда не используем портретное фото человека
напрямую как og:image: соцсети (особенно Facebook) обрезают по
центру по ширине, у портрета 3:4/4:5 при такой обрезке лицо почти
гарантированно уходит за край или в кроп попадает только часть лица.

**Личные фото команды** (`abdulova`/`moshnikov`/`bychkova`/`alena-
bychkova`/`kazmiruk`/`sachkov`) — все шесть исходников портретные
(соотношения от 3:4 до 4:5). Для каждого сделан отдельный файл
`images/<slug>-og.jpg` (1200×630) — умный кроп по лицу
(распознавание через OpenCV `haarcascade_frontalface_default`,
координаты подобраны так, чтобы над головой оставался небольшой
отступ, а не строго по центру лица — иначе макушка обрезается
вплотную) и подключён ТОЛЬКО в `og:image`/`twitter:image`. Сам
исходный портретный файл (`images/<slug>.jpg`) не менялся и
по-прежнему используется на странице (`<img>`) и в `Person.image`
(JSON-LD) — там уместнее полный портрет, не социальный кроп.
Если/когда фото человека обновится — новый `og:image`-вариант нужно
пересчитать заново тем же способом, автоматически он не обновляется.

**Как считался кроп (для повторения на новых фото):** haarcascade
находит `(x, y, w, h)` лица в пикселях исходника → берём центр `(fx,
fy)` → верх кропа = `fy - crop_h × 0.42` (не `fy - crop_h / 2` —
формула на центр лица обрезает волосы/лоб) → кроп по ширине/высоте
исходника с этим отступом, ограниченный границами кадра → resize до
1200×630. На одном фото (`alena-bychkova.jpg`) детектор дал два
результата (одно ложное — текстура фона слева) — использовалось
глазами проверенное настоящее лицо, не оба вслепую. Скрипт
одноразовый, не сохранён в `_tools/` — при следующей необходимости
переписывается заново по этому описанию.

## Структурированные данные (schema.org / JSON-LD, aelita-v46)

Каждая страница со своим `<script type="application/ld+json">` в
`<head>` — единственный (не несколько отдельных тегов на странице).
Если у страницы несколько сущностей (например, тизер-видео и сам
спектакль) — они не отдельными тегами, а узлами одного `@graph`.

**JSON-LD не переводится пайплайном `_tools/DesignSystem/i18n/`** —
`build_en.py` пропускает содержимое `<script>` при переводе (см.
`core.py`, `if el.tag in ('script','style'): continue`), поэтому на
EN-страницах структурированные данные остаются на русском — это уже
было так до aelita-v46 (см. `VideoObject` на `/en/porfiriy` и т.д.) и
осознанно не меняли: разметка не показывается пользователю напрямую,
несоответствие языку `<html lang>` для Google/Яндекса не проблема,
а дублировать контент на двух языках вручную — источник расхождений.

**Типы, которые используются, и почему:**
- `Organization` — только на главной, единственный источник данных о
  компании для Google Knowledge Panel. `logo` обязателен ссылкой на
  РЕАЛЬНО существующий файл — раньше ссылался на несуществующий
  `/logo.png` (пойман и исправлен в aelita-v46), теперь на
  `/icons/icon-512x512.png`. Если меняете `logo` — сначала `curl -I`
  на новый URL, не полагайтесь на память, что файл там есть.
- `TheaterEvent` — репертуарные спектакли без известной даты
  следующего показа (`meydey`/`mozgi`/`rasyomon`/`rozovoe-maslo` были
  так с более ранних версий; `porfiriy`/`iov`/`jazz_dance`/`listen`/
  `stories`/`instruction`/`human`/`corner` получили его в aelita-v46,
  добавлен вторым узлом `@graph` рядом с существовавшим `VideoObject`,
  сам `VideoObject` не менялся).
- `Event` — только там, где известна конкретная дата показа
  (`/iov`, дублирует данные из `Event` на главной, `/tochkacuire`).
  Дата истекает — не забыть снять/обновить `Event`, когда показ
  пройдёт (иначе Google может понизить доверие к структурированным
  данным сайта за просроченные события).
- `Festival` — подтип `Event`, только `/tochkacuire` (сама страница
  фестиваля; на главной для фестиваля тоже `Event`, не дублировали

- `PerformingGroup` — `/koroche` (это компания, не спектакль).
- `Product` + `Offer` — `/community`, `/book-concierge`,

  разовая покупка; у gift-card через `PriceSpecification` с
  `minPrice`/`maxPrice`, а не фиксированный `price`, — сумма любая).
- `ItemList` — `/shop`, оборачивает те же четыре `Product`, что и на
  их собственных страницах (сознательно продублировано, не

**Отзывы и рейтинг — только настоящие, без исключений.**
`_tools/Reviews/` пока не задеплоен (`REVIEWS_API_URL` в
`assets/reviews.js` — заглушка), реальных отзывов физически нет.
`aggregateRating` НЕ прописан вручную ни на одной странице — вместо
этого `assets/reviews.js` (функция `updateAggregateRatingSchema`,
aelita-v46) сама досчитывает средний балл и число отзывов из того,
что реально пришло с бэкенда, и дописывает `aggregateRating` в узел
`@graph` с `@id`, оканчивающимся на `#event` (это есть на всех 8
страницах с виджетом отзывов: `porfiriy`/`iov`/`jazz_dance`/`listen`/

появляется вообще, и это правильно: Google и Яндекс блокируют/штрафуют
сайты за рейтинг, который нельзя подтвердить на самой странице.
**Если добавляете новую страницу спектакля с виджетом отзывов — дайте
её `TheaterEvent`/`Event` тот же `@id`-паттерн (`.../<slug>/#event`),
иначе рейтинг для неё считаться не будет.**

**Проверка перед сдачей:** валидность JSON построчно не проверяется
глазами — гоняли одноразовым скриптом (`json.loads` на каждый
`<script type="application/ld+json">` по всему `Site/`, RU и EN).
Постоянной проверки в `run_audit.py` для этого пока нет — стоит
завести, если структурированные данные будут расширяться дальше
(например, проверять, что `@id` совпадает с `canonical` страницы).

## `.page-hero` — один класс, два разных смысла

На части страниц `.page-hero` — простой текстовый блок (заголовок + подпись,
статичный фон, обычный `padding`). На страницах с видео на весь экран
(`porfiriy`, `iov`, `gogol`, `koroche`, `tochkacuiri`, `listen`, `stories`,
`instruction`, `jazz_dance`) тот же класс переопределён **локально** под
принципиально другую вёрстку: `position:relative;min-height:100svh;
display:flex;padding:0`, а фон/видео рисуют соседние `.hero-bg`/
`.hero-overlay`/`<video>`. Если добавляешь новую страницу с видео-хиро —
бери за образец одну из этих, а не общий `.page-hero` из `assets/style.css`.

## `.hero-sub` — тоже один класс, два разных смысла

Тот же паттерн, что и с `.page-hero` (см. выше), только вскрылся позже.
В `assets/style.css` `.hero-sub` — это маленькая подпись капслоком с
трекингом (стиль-«эйбрау» под заголовком: `porfiriy`, `gogol`, `iov`,
`koroche`, `tochkacuiri`). А на `community` и `team` тот же класс — обычный
абзац текста обычным регистром. Локальные правила на этих двух страницах
переопределяли только размер/цвет/отступы, но не `text-transform`/
`letter-spacing`/`font-family` — эти три свойства утекали из общего файла,
и текст на вид оставался капслоком, что бы ни делали с размером шрифта.

**Общий урок** (уже два случая — `.page-hero`, `.hero-sub` — считай, что
будут ещё): если на сайте есть класс, который на одних страницах значит
«маленькая подпись-эйбрау», а на других — «обычный текст», при любой правке
такого класса **переопределяй вообще все визуальные свойства локально**, а
не только те, что меняешь по задаче. Иначе на глаз кажется, что поправил
размер — а капслок/трекинг/шрифт остались от чужого контекста, и результат
выглядит «как будто не подействовало».

## Плавающая нижняя плашка и футер

На части страниц внизу есть фиксированный элемент — либо кнопки-CTA
(`.mob-cta`, показы/билеты, только `porfiriy`/`iov`/`tochkacuiri`), либо
кнопка Telegram (`.tg-widget`, все остальные обычные страницы — 33 шт).
Оба перекрывают низ экрана на мобильных. Если у страницы есть любой из
них — у футера обязательно должен быть запас снизу (`padding-bottom` в
медиа-запросе `≤760px`/`≤430px`), иначе реквизиты и ссылки в футере
окажутся под плашкой при докрутке до конца.

**Важно про `.tg-widget`:** у него не фиксированная высота. Периодически
(по таймеру, через JS) над кнопкой всплывает бабл-подсказка
(«Напишите нам — бот ответит мгновенно», `.tg-bubble`), и в этот момент
весь виджет становится примерно в 2 раза выше, чем просто кнопка. Запас
в футере нужно считать на **виджет с открытым бабблом**, а не на кнопку
одну — иначе в момент появления баббла он будет наезжать на футер. Текущее
значение — `210px`/`230px`, взято с запасом от расчётной высоты
(отступ снизу 70px + бабл ~60-80px + кнопка ~44px + зазоры).

## Страницы под конкретную аудиторию (`business`, `event`, `creativity`, `venues`, `partners`)

Четыре страницы (`business`/`event`/`creativity`/`venues`) — один и тот
же шаблон: герой (заголовок + буллиты) → форма с полями именно под эту
аудиторию → тот же общий футер. Пятая, `/partners`, — та же идея
(герой → форма → футер), но собрана отдельно, с другим паттерном формы
(см. ниже) — не копируй её как образец вместе с первыми четырьмя.
`/collaboration` собирает все пять направлений (включая «Партнёрам и
инвесторам», которые физически ведут на `/business`) в виде табов и
просто ссылается на эти страницы. Если добавляешь новую аудиторию —
копируй один из первых четырёх файлов целиком как основу, а не собирай
с нуля.

У форм `business`/`event`/`creativity`/`venues` — свой суффикс id
(`_b`, `_e`, `_c`, `_v` — не `_bz`/`_ev`/`_cr`/`_vn`, как ошибочно было
написано здесь раньше) и своя функция `handleForm(id)`, которая знает
именно про её поля. Общий шаблон формы (через `select`+один `textarea`)
подходит не всем — если в форме несколько текстовых полей с разным
смыслом (как в `venues` — техника, даты, пожелания), `handleForm` там
переписан вручную под конкретные `id` полей, копипаст общей версии
потеряет данные.

`/partners` — пятая аудиторная страница, но её форма устроена иначе:
без цифрового суффикса (`fname`/`femail`/`fphone`/`fmsg`/`ftype`) и с
`handleForm()` без аргумента. Если копируешь `business`/`event`/
`creativity`/`venues` как образец для новой аудитории — не путай с
`/partners`, эти два паттерна не взаимозаменяемы.

`/collaboration` не имеет собственной формы — она просто ссылается на
эти пять страниц (см. выше).

## `display` у `.btn-outline` / `.btn-gold` — не удаляй молча

У этих классов бывает локальное переопределение вида `.btn-outline{display:inline}`
на нескольких страницах (`gogol`, `porfiriy`, `tickets`, `iov`) — оно там
специально, не мусор. Но **должно быть `inline-block`, не `inline`**: если
текст кнопки длинный и переносится на две строки (например, «Узнать о новых
датах»), у `inline`-элемента рамка не может аккуратно обернуть многострочный
текст — вылезают наползающие друг на друга линии. `inline-block` эту
проблему не имеет и всегда безопасен для кнопки с рамкой/паддингом.

## Плашки на `position:fixed` — считай реальную высоту шапки

Была страница (`/gogol`), где баннер «Архивный спектакль» стоял
`position:fixed;top:0` с `margin-top:60px`, чтобы отступить от шапки — но
шапка выше 60px, и баннер под неё залезал. Если элементу обязательно нужно
быть `fixed` поверх контента — не подбирай отступ на глаз под конкретный
брейкпоинт, высота шапки meняется (там сам логотип в две строки). Надёжнее
вообще не фиксировать такие второстепенные баннеры, а оставить в обычном
потоке документа сразу после шапки — так он гарантированно не наложится,
пусть и уедет при скролле вместе со страницей.

### Кнопки сайта: реальный баг с контрастом, не косметика (`aelita-v35`)

По прямой просьбе заказчика («посмотри все кнопки, они как-то
странно выглядят», со скриншотами) — найдена и исправлена настоящая
причина, не то же самое, что случайный визуальный сбой:

1. **`.btn-outline` не сбрасывал `background`.** На `<a>` это
   незаметно (фон и так прозрачный по умолчанию), но там, где та же
   разметка применена к настоящему `<button>` (например, «Сначала
   спросить Катю» на `/community`) — браузер подставляет свой
   системный фон кнопки, который забивает светлый `color:var(--bone)`
   в нечитаемый низкоконтрастный текст. Ровно то, что было видно на
   присланном скриншоте.
2. **Нигде на сайте не был объявлен `color-scheme:dark`.** Часть
   Android-браузеров (по виду скриншотов — старый Samsung Internet)
   применяет собственную эвристику принудительной тёмной темы к
   страницам, не заявившим свою цветовую схему явно — она может
   ломать контраст отдельных элементов непредсказуемо. Вероятная
   причина второго скриншота — полностью пропавший текст на золотой
   кнопке (`<a class="btn-gold">`, обычная ссылка, так что первая
   причина её не объясняет).

**Масштаб:** не единичная правка. Общий `assets/style.css` — да, но
**40 страниц** дублируют `.btn-outline`/`.btn-gold`/`:root` инлайново
в собственном `<style>` (переопределяют общий файл по каскаду — фикс
только в assets/style.css их бы не затронул). Написан и прогнан
скрипт, который нашёл все инлайн-дубликаты и точечно добавил
недостающие свойства (`background:none`, `-webkit-appearance:none`,
`cursor:pointer` для `.btn-outline`; `appearance`-резет для
`.btn-gold`; `color-scheme:dark` в `:root`), сохранив у каждой
страницы её собственные `padding`/`margin`. Отдельно поймана и
исправлена генератор-функция `Site/_generators/build_show_page.py` —
без этой правки каждая новая страница спектакля, созданная им,
воспроизводила бы тот же баг заново.

**Заодно найдена и исправлена независимая рассинхронизация**, не
связанная с кнопками напрямую: `sw.js` уже объявлял `SITE_VERSION =
19`, `main.js?v=` на всех страницах был обновлён до 19 в прошлой
правке, но `style.css?v=` остался на 18 — не заметили тогда. Поднято
до 19 на всех 100 HTML-страницах, заодно стало кэш-бастингом для
самой этой правки.

`_tools/Audit/run_audit.py` — добавлены 2 новых паттерна в
`KNOWN_BAD_PATTERNS`, с новой возможностью (её раньше не было) сузить
проверку конкретного паттерна до подпапки пака через необязательный
третий элемент кортежа — понадобилось, потому что «нет `background:`»
и «нет `color-scheme`» осмысленны только для живых HTML-страниц
`Site/`, не для PDF/печатных шаблонов в других частях пака
(`Brand/07_AELITA_flyers/`, `_tools/GuestSystem/ticket.html`,
`_tools/DesignSystem/setup-guides/`), где браузерный форс-дарк и
настоящие `<button>` не участвуют вообще — без сужения оба паттерна

законно упоминает старый текст, был упущен раньше).

Проверено: `check_i18n.py` — чисто (правка чисто CSS, новых строк для
